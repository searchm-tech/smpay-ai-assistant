# 설계 문서 — SM Pay 내부 문서 기반 LLM 답변(RAG)

> 결정과 이유를 날짜와 함께 누적 기록한다. 상태: **초안, 승인 대기 항목은 "열린 질문"에 표시**

## 1. 목표와 범위

- 질문과 관련된 Notion 문서를 찾아, 그 문서를 근거로 **출처와 함께** 답한다(RAG).
- 관리자 UI 자연어 인터페이스는 이 검색 결과를 컨텍스트로 쓸 수 있는 **구조만** 만든다(6단계).
- 기존 `smpay-ai-conversation-pipeline`은 건드리지 않고, 이 레포에서 처음부터 새로 구현한다.

### A2 실측 (2026-10-16, 맥북 Intel CPU, torch 2.2.2)

| 항목 | 값 | 설계에 주는 의미 |
|---|---|---|
| 모델 | KURE-v1, 1024차원, 약 2.1GB(safetensors), 메모리 약 2.3GB | embedder 상시 구동에 RAM 약 3GB 확보 필요 |
| 질문 1건 임베딩 | 약 430ms | 요청마다 발생 → 챗 응답 지연에 그대로 더해짐 (터널 왕복 별도) |
| 500자 청크 | 약 1.5초/건 | 청크 1,000개 ≈ 26분, 10,000개 ≈ 4.3시간 (최초 백필 한 번). 일 배치는 변경분만이라 부담 작음 |
| 유사도 | 관련 0.817 / 무관 0.333 | 한 문장 짧은 쌍 기준. 실제 청크 기준 점수 분포는 A7 라벨링 평가에서 결정 |
| 기본 max_seq_length | 8192 | CPU에서 긴 입력은 지연이 커지므로 서비스(A3)에서 상한(예: 512)을 두는 것을 제안 → 청크 크기와 함께 A3/A6에서 확정 |

> Windows 데스크탑의 수치는 CPU/GPU에 따라 다르므로 B1에서 같은 `scripts/smoke_test.py`로 다시 측정한다.
> 현재 lock은 CPU용 torch이므로 GPU를 쓰려면 CUDA torch로 따로 구성해야 한다.

### A3 임베딩 서비스 설계 (2026-10-16 확정, 구현 완료)

> 구현 중 추가한 결정: 인증은 본문 파싱 **전에** 미들웨어에서 검사(잘못된 본문으로도 정보를 얻지 못하게), `Content-Length` 없으면 411·1MB 초과 413,
> `/docs`·`/openapi.json` 비활성(터널 노출 대비), 500은 예외 종류만 로그하고 응답은 일반화. 알려진 한계: 요청마다 서버 측 추론 시간은 짧지만(약 0.2초)
> 터널 왕복·직렬 대기는 별도이며, 인증 실패 횟수 제한(brute-force 방어)은 아직 없음 → B3(Cloudflare 앞단)·7단계에서 보강.

- **API**: `POST /embed {texts[]}` → `{model, revision, dim, embeddings[][], truncated[]}` (입력 순서 유지, 길이 1 정규화).
  query/document 구분·접두사는 두지 않음(KURE-v1은 불필요). `model`/`revision`은 A4에서 청크별로 저장해 재임베딩 대상 식별에 사용.
- **인증**: `x-internal-secret` ↔ `EMBEDDER_SECRET`, `hmac.compare_digest`. 없음/32자 미만이면 기동 거부(fail-closed). 없음·틀림 모두 동일 401.
  `127.0.0.1`에만 바인딩. 터널 앞단 Cloudflare Access 서비스 토큰은 B3에서 재검토.
- **제한**: 요청당 32개, 텍스트당 4,000자 초과 422, 토큰 512 초과는 **자르고 `truncated:true`**(결정), 본문 1MB.
- **동시성**: 추론 **직렬 1건씩 + 대기 8건 초과 시 503(`Retry-After`)**(결정), 워커 1개. 챗 서버의 짧은 타임아웃·안전한 실패는 A8.
- **`/health`**: **인증 없이 `{"status":"ok"}`만**(결정). 모델 로딩+워밍업 후에만 기동.
- **로그/오류**: 요청 ID·개수·총 글자 수·소요 시간·상태코드만. 텍스트 미기록, 422 응답/로그에서 입력값 제거. `HF_HUB_OFFLINE=1`.
- **테스트(실패 케이스 우선)**: 401 동일 응답 / 비밀값 없음·짧음 기동 실패 / 422 경계값 / 입력값 비노출 / truncated / 503 / 순서·차원·정규화 / health 무인증 / (느린) 실제 모델 유사도 순서.

### A4 Supabase + pgvector 스키마 설계 (2026-10-16 확정, 구현·로컬 검증 완료 / 실제 Supabase 적용 대기)

- **테이블**: `documents`(Notion 페이지 1행: `notion_page_id` unique, title, url, breadcrumb, `content_hash`, `notion_last_edited_at`, `synced_at`),
  `chunks`(`document_id` FK **on delete cascade**, `chunk_index`, `heading_path`, content, `token_count`, `truncated`,
  `embedding vector(1024)`, `embedding_model`, `embedding_revision`, unique(document_id, chunk_index)).
  삭제된 문서는 soft delete 없이 행을 지워 벡터도 함께 제거(삭제 문서가 검색에 남는 것이 가장 위험).
  모델/버전을 청크마다 저장 → 재임베딩 대상 식별, 검색은 **같은 revision끼리만** 비교.
- **함수**: `replace_document(...)`(문서 upsert + 청크 교체를 한 트랜잭션, 실패 시 옛 청크 유지),
  `match_chunks(임베딩, revision, limit, 후보 문서 id 배열|null)`(cosine 유사도 = 1 − 거리, 후보 id는 지금 항상 null이지만 권한 필터용 자리),
  `delete_documents_not_in(...)`(동기화 시 삭제 정리, A6).
- **접근 방식(결정)**: REST+secret 키 대신 **직접 Postgres 연결 + 역할 분리**. `chat_reader`는 `match_chunks` 실행만, `ingest_writer`는 쓰기 함수만.
  이유: 챗 서버(Vercel)가 유출돼도 검색만 가능 → **청크에 지시문을 심는 인덱스 오염(프롬프트 인젝션) 방지**. 두 테이블은 RLS 켜고 정책 없음(anon 차단), 함수는 PUBLIC 실행 권한 회수.
  역할 비밀번호는 마이그레이션 SQL에 쓰지 않고 `.env`의 값으로 스크립트가 설정(커밋 금지).
- **마이그레이션(결정)**: `sql/NNN_*.sql` 추가 전용 + `scripts/apply_migrations.py`가 번호순 적용하고 적용 기록 테이블(`schema_migrations`)에 남김. 코드 배포 전에 DB 먼저.
- **인덱스**: A4에서는 만들지 않음(정확 검색). 순위가 흔들리는 근사 인덱스는 A7 기준 점수 평가를 어지럽힘. 용량: 청크 1개 약 6KB → 1만 개 약 60MB(무료 500MB 이내).
  - **실측(2026-10-16, 로컬 Docker pgvector 17, Intel Mac CPU)**: 합성 2만 청크 정확 검색 **왕복 약 220ms**(DB 내부 210~300ms). 즉 1천 청크당 약 10ms.
    **설계 시 "수십 ms 안쪽"이라 한 추정은 낙관적이었다.** 1만 청크면 약 100ms, 5천이면 약 50ms로 추정. 실제 Supabase 무료 티어(공유 CPU)는 다를 수 있어 **적용 후 재측정 필요**.
  - **결정 보류 → A5에서 실제 청크 수가 나오면 확정**: 약 5천 이하면 인덱스 불필요, 약 1만 이상이면 HNSW 도입 검토. 도입 시에도 A7에서
    **정확 검색 결과를 정답으로 삼아 recall@k ≥ 0.99를 확인**한 뒤 적용(질문 임베딩에 이미 약 0.2초 + 터널 왕복이 들므로 DB 지연 예산을 함께 본다).
- **구현 중 추가·발견한 것**: (1) `match_chunks`는 질문 벡터 차원이 1024가 아니면 **오류를 낸다** — 검증 전 버전은 청크가 하나도 없을 때 차원이 틀려도 조용히 빈 결과를
  돌려줘 임베딩 버그를 가릴 수 있었음. (2) `match_chunks(후보 id=[])`는 "제한 없음"이 아니라 **"후보 없음"** (빈 배열이 권한 우회가 되지 않게). (3) 역할 설정(`statement_timeout`)은
  DB가 아니라 클러스터 전체에 저장되고 마이그레이션은 1회만 실행되므로, 누가 역할 설정을 초기화하면 이탈한다 → 테스트가 감시. (4) 적용 기록 체크섬은 줄바꿈(CRLF/LF)을 정규화해 Windows 체크아웃에서 오탐이 없게 함.
  (5) 역할 비밀번호는 평문 `ALTER ROLE ... PASSWORD` 대신 **클라이언트에서 만든 SCRAM-SHA-256 검증값**으로 설정(서버 로그에 평문이 남지 않음).
- **검증 범위와 한계**: 로컬 일회용 PostgreSQL 17 + pgvector(Docker)에 Supabase의 기본 역할·기본 권한(anon/authenticated 자동 부여)을 흉내 내어 검증.
  SQL 정적 검사 + 변형 테스트(SQL 12종, 전부 탐지) + 실제 DB 테스트 19개 + 실제 KURE-v1 벡터 end-to-end 통과.
  **로컬과 Supabase의 차이로 아직 미검증**: 풀러(Supavisor) 연결·사용자명 `역할.프로젝트ref`(R8), Supabase의 비-superuser `postgres` 권한, 실제 지연 → 프로젝트 생성 후 같은 테스트로 확인.
- **범위 밖(의도적 보류)**: `sync_runs` 같은 배치 이력 테이블(A6에서 추가), Notion 블록 단위 딥링크(추가로 가능), 대화 로그 저장(로그에 본문을 남기지 않는 원칙).
- **테스트(실제 Supabase, 롤백 트랜잭션)**: anon 차단 / 역할별 실행 권한 / 차원 불일치 거부 / 중복·cascade / `replace_document` 원자성 / 재동기화 시 청크 수 불변 /
  revision·삭제 문서 제외 / A3 실제 벡터로 순서 확인 / 합성 2만 건 지연.
- **위험 R8 — 연결 방식**: Supabase 직접 연결(db.<ref>.supabase.co)은 IPv6 위주라 Vercel·사내망에서 안 될 수 있음 → **Supavisor 풀러**
  (챗 서버는 트랜잭션 모드 6543 + prepared statement 비활성, 마이그레이션·배치는 세션 모드 5432). 풀러에서는 사용자명이 `역할.프로젝트ref` 형식. A4에서 실제로 연결해 확인한다.
- **위험 R9 — 무료 티어 일시정지**: 무료 프로젝트는 1주 무활동 시 정지됨. 일 1회 동기화 배치가 DB를 호출하므로 사실상 방지되지만, 배치가 멈추면 정지될 수 있음(운영 단계에서 모니터링).

### A5 Notion 수집 설계 (2026-10-16 확정, 구현·가짜 응답 검증 완료 / **실제 Notion 응답은 미검증**)

**공식 문서로 확인한 사실** ([markdown 엔드포인트](https://developers.notion.com/reference/retrieve-page-markdown), [markdown 가이드](https://developers.notion.com/guides/data-apis/working-with-markdown-content), [요청 한도](https://developers.notion.com/reference/request-limits)):
`GET /v1/pages/{id}/markdown`(`Notion-Version: 2026-03-11`)이 페이지를 마크다운(v1, 헤딩 `#`~`####`, 표·콜아웃·토글은 `<table>`/`<callout>`/`<details>` 태그)으로 반환.
응답에 수정 시각 없음. 하위 페이지·DB는 `<page url>`/`<database url>` 태그로만 나오고 펼쳐지지 않음. 미공유 자식은 `<unknown>`, 약 2만 블록 초과는 `truncated`,
`unknown_block_ids`로 후속 조회(접근 불가는 404). 북마크·임베드·링크프리뷰는 미지원(`<unknown>`). 한도: 연결당 분당 180회, 초과 시 429 + `Retry-After`, 529 재시도.
마크다운 세부 태그(멘션 등)는 문서에 완전히 없음 → 구현 초반 실제 응답으로 **구조만** 확인해 fixture로 고정.

- **실행 위치(결정)**: 회사 데스크탑. 최초 백필이 수 시간일 수 있어 Vercel cron 제한과 맞지 않고, 임베딩 서비스와 같은 머신이라 터널 불필요.
  **Notion 토큰·`ingest_writer` 비밀번호는 데스크탑에만** 두고 챗 서버(Vercel)는 `chat_reader`만 가짐 → 챗 서버가 털려도 인덱스 오염 불가. 꺼진 날은 건너뛰고 다음 실행에서 따라잡음.
- **접근 권한**: Notion **내부 통합, "Read content" 권한만**(수정·댓글·사용자 정보 권한 없음). 허용 목록은 두 겹: ① Notion에서 루트 페이지만 통합에 공유 ② `NOTION_ROOT_PAGE_IDS` 아래로만 크롤.
  루트 목록이 비면 **시작 거부(fail-closed)**, 워크스페이스 전체로 확대하지 않음. 페이지 URL을 넣어도 ID 추출.
- **수집**: 루트에서 BFS 크롤(페이지마다 메타데이터 조회 + **markdown 조회(매번 전부)** → `<page>` 태그로 자식 발견, 방문 집합·상한 가드). **DB 행은 건너뛰고 개수만 보고(결정)**.
- **정제**: 이미지·파일·비디오·PDF의 **pre-signed URL은 버리고 캡션/파일명만 유지**(만료 토큰이 DB·LLM 컨텍스트에 남는 것 방지 + 매번 달라 매일 "변경"으로 오인되는 것 방지),
  `<unknown>`·목차·custom-block 제거 후 개수만 집계, 표는 `셀 | 셀` 행으로 변환, 콜아웃·토글·컬럼·동기화 블록은 안쪽 텍스트로 평탄화, 하위 페이지는 제목만 남기고 자식 문서로 등록,
  사용자 멘션은 표시 이름만(ID·URL 제거), 헤딩은 유지(A6 청크 경계). **정제는 멱등**, 정제 후 텍스트의 해시를 변경 판단 기준으로 사용.
- **변경 감지(일 1회) — 구현 중 설계 정정(2026-10-16)**: 승인된 설계는 "`last_edited_time`이 같으면 markdown 조회를 생략"이었으나 **그러면 크롤이 깨진다** —
  하위 페이지는 부모 markdown의 `<page>` 태그로만 발견되므로 변경 없는 페이지를 건너뛰면 그 아래 문서를 못 찾는다. 그래서 **모든 페이지의 markdown을 매번 조회**하고(페이지당 호출 2회:
  메타데이터 + markdown, 300페이지 약 4분 / 1,000페이지 약 14분), 변경 판단은 **정제 텍스트 해시**로 한다(해시가 같으면 재임베딩 안 함). 이 때문에 "주 1회 전체 재해시" 안전망은 불필요해졌다
  (매번 전체를 해시). 문서가 1만 페이지 규모로 커지면 부모-자식 관계를 DB에 저장해 변경 없는 페이지를 건너뛰는 최적화를 다시 검토한다.
  상태는 `new / changed / metadata_only(해시 같고 시각·제목·breadcrumb만 다름) / unchanged` 4가지이고, 본문(`text`)은 new·changed일 때만 채운다.
  저장된 상태는 DB에서 읽어야 하는데 `ingest_writer`는 테이블을 못 읽으므로 **A6에서 `get_sync_state()` 함수를 마이그레이션 002로 추가**. A5는 상태를 인자로 받아 DB 없이 테스트.
- **크롤 완전성 플래그(안전장치)**: 재시도 후에도 실패한 호출이 있거나 상한에 걸리면 `complete=false` → A6는 `delete_documents_not_in` 호출을 **건너뜀**(일부만 수집된 목록으로 삭제하면 멀쩡한 문서가 지워짐).
- **한도·오류**: 초당 약 2.5회(설정 가능), 429는 `Retry-After` 준수, 529/503/504는 지수 백오프 최대 5회, 타임아웃 30초. 오류·로그에 **토큰과 문서 본문 미기록**(페이지 ID·오류 종류만).
- **측정 리포트(본문 없는 집계만)**: 문서 수·깊이·글자 수 분포(p50/p90/p99)·`truncated`/`unknown` 수·건너뛴 DB 수·**민감정보 패턴 적중 수**(사업자번호·주민번호·카드번호·이메일·전화번호·API 키 모양·서명 URL·"비밀번호" 키워드)를
  페이지별 **개수로만** 출력(매칭 값은 출력 안 함). A6의 청크 크기와 A4에서 보류한 인덱스 도입 여부의 입력.
- **구조**: 새 폴더 `ingest/`(uv 프로젝트, 의존성은 `httpx` 위주). 설정 `.env`에 `NOTION_TOKEN`, `NOTION_ROOT_PAGE_IDS`.
- **테스트(실패 케이스 우선, 전부 네트워크 없이 가짜 Notion 응답)**: 정제(서명 URL이 어떤 입력에서도 남지 않음 속성 테스트 / 멱등 / 서명 URL만 다른 두 응답의 해시 동일 / 표·콜아웃·토글),
  클라이언트(429·백오프·재시도 한계·404·토큰이 예외·로그에 없음), 크롤러(허용 목록 밖 페이지는 호출 자체가 없음 / 중복·순환 방지 / `unknown_block_ids` 후속 조회 / 상한 / 실패 시 `complete=false`),
  변경 감지(시각 같으면 markdown 호출 0회 / 해시 같으면 재임베딩 없음 / 삭제 판정은 `complete=true`일 때만), 리포트·스캐너(본문·매칭 값 비노출), 설정(토큰·루트 없음 거부).
- **구현 결과(2026-10-16)**: `ingest/notion_ingest/`(`ids`, `config`, `notion_client`, `cleaner`, `scanner`, `crawler`, `report`, `cli`). 테스트 119개(전부 네트워크 없이 가짜 Notion — 개별 단위 + 실제 `NotionClient`를
  HTTP 레벨 가짜 서버에 붙인 통합 3개). **변형 테스트 28종(허용 목록 우회·삭제 안전장치·서명 URL·토큰/본문 유출·429 처리 등) 전부 탐지.**
  추가로 정한 것: 허용 목록은 "태그가 보이는가"가 아니라 **실제 부모가 이 페이지인지(`parent.page_id` 일치)** 로 검증 — `link_to_page` 블록이 허용 목록 밖 페이지를 가리켜도 본문은 가져오지 않고 개수만 센다
  (단 부모 검증을 위해 그 페이지의 **메타데이터(제목 등)는 한 번 조회**됨, 저장하지 않음). 부모가 `block_id`인 하위 페이지는 보수적으로 건너뛰고 개수를 보고(R12). 루트가 안 보이면(`root_not_found`) 하위 문서가
  전부 "사라진 것"처럼 보이므로 크롤을 **불완전**으로 표시해 삭제를 막는다. 잘린(truncated) 페이지만 `unknown_block_ids`를 후속 조회(상한 20, 초과 시 `partial`)하고, 미지원 블록까지 조회해 호출이 폭증하는 것을 막는다.
- **알려진 한계 / 미검증**: ① Notion 마크다운의 **실제 응답 형식은 공식 문서 기반 추정**이다(특히 멘션 태그, 표·콜아웃의 정확한 모양) — 실제 응답으로 대조해 `tests/fixtures.py`와 `cleaner.py`를 맞춰야 한다(R11).

- **위험 R12 — 하위 페이지 부모 유형**: Notion에서 토글·컬럼 안에 만든 하위 페이지의 `parent`가 `block_id`로 오는 경우가 있으면 그 문서들이 수집에서 빠진다. 리포트의 `unverified_children_skipped`가 0이 아니면

| 임베딩 서버가 `truncated`라고 한 청크는 **반으로 나눠 다시 임베딩**(최대 2회), 그래도 잘리면 `truncated` 표시 저장. `/embed` 응답에 `token_counts` 추가(A3 변경, 기존 필드 호환) | 512토큰 초과 입력의 뒷부분이 조용히 검색에서 사라지는 것을 막고, DB `token_count`를 추정이 아닌 실제 값으로 채움 |
| 임베딩 서버 장애: 문서 하나의 실패는 격리, **연속 3번 실패하거나 인증 실패·revision 변경이면 중단**, 시작 전 사전 점검 실패 시 DB·Notion을 건드리지 않음 | 죽은 서버를 두드리지 않고, 한 문서의 청크는 모두 같은 revision 이어야 한다 |
| 삭제는 **크롤이 완전 + 쓰기 실패 0 + 중단·미처리 없음 + 대량 삭제 가드 통과**일 때만. 가드: 삭제 후보가 `max(1, min(10, 전체의 20%))`개를 넘으면 거부, `--force-delete`로만 진행 | 일부만 본 목록·API 이상으로 문서가 대량 삭제되는 사고 방지. 크롤러·동기화 양쪽에서 각각 막는다(둘 다 변형 테스트로 확인) |
| **민감정보 격리**: 고위험 패턴(주민번호·카드번호·API 키 모양·"비밀번호:" 대입)이 보인 문서는 **기본적으로 색인하지 않고 리포트(id·패턴 이름)에만** 올림. 사람이 확인한 문서는 `INGEST_ALLOW_SENSITIVE_PAGE_IDS`로 허용. 이미 색인된 문서가 새로 걸리면 크롤 완전성과 무관하게 즉시 삭제. 이메일·전화·사업자번호는 보고만 | "문서에 고객·결제 정보가 없다"는 외부 LLM 전송 허용의 전제를 기술적으로 강제. 오탐(16자리 숫자, "token:" 등)은 허용 목록으로 푼다 |
| 동시 실행 방지: 전용 연결의 advisory lock(세션 단위, 프로세스가 죽으면 서버가 해제) | 맥북 테스트와 데스크탑 운영이 겹치지 않게. **풀러는 세션 모드(5432)여야 함** |
| 마이그레이션 `002_sync.sql`(추가 전용): `index_signature`, `get_sync_state`, `update_document_metadata`, `delete_document`, `sync_runs`+`start/finish_sync_run`. `replace_document`는 서명 인자를 받는 8인자로 교체(**옛 7인자 삭제**) | 서명 없이 쓰는 경로가 남지 않게. `sync_runs`는 정수 컬럼과 `[a-z0-9_]{1,40}` 사유 코드만 받도록 **DB가 강제**(본문·제목·id를 담을 자리가 없음) |
| 접속: `INGEST_DATABASE_URL`(ingest_writer) 우선, 없으면 관리자 URL 호스트+`INGEST_WRITER_PASSWORD`로 구성(개발용) | 운영 데스크탑에는 관리자 비밀번호를 두지 않는다 |
| 실패 알림은 **나중에 결정**(B4). 지금은 로그·종료 코드(0 성공 / 1 불완전·실패 / 2 설정 오류)·`sync_runs` | 사용자 결정(2026-10-16) |
| e2e·잠금 테스트는 **로컬 호스트의 빈 DB에서만** 실행 | e2e는 "없는 문서를 지우는" 동기화를 실제로 실행하므로 운영 DB 보호 |

명령: `cd ingest && .venv/bin/python -m notion_ingest sync [--dry-run] [--limit N] [--force-reindex] [--force-delete] [--json]`
(`--dry-run`은 임베딩 서버 사전 점검과 DB 읽기만, 쓰기·락·실행 기록 없음. `--limit`은 삭제를 건너뜀.)

검증(2026-10-16): ingest 264개(환경변수 없이 248 + 로컬 DB·컨테이너 16, 실제 KURE 컨테이너+Postgres+가짜 Notion end-to-end 4개 포함), sql 104, embedder 36(+실제 모델 1).
변형 테스트(소스를 일부러 망가뜨려 테스트가 실패하는지 확인): 청커 12종·임베딩 클라이언트 12종·동기화 34종·CLI 11종·설정 6종·저장소 8종·SQL 16종·크롤러 4종. 처음 미탐지였던 항목은 테스트를 보강한 뒤 다시 확인해 모두 탐지됨(아래).
처음 미탐지였던 것(보강함): 긴 문장 마지막 조각 유실, 코드 블록 안 빈 줄 분리, 오류 메시지에 DB 행 내용 포함(Postgres CHECK 위반 DETAIL), 음수 건수 검사, 가드 한도 상한, 불완전 크롤·limit·중단 시 삭제 방어, breadcrumb 저장.

**한계·미검증**: ① 실제 Notion 응답 형식(R11)·실제 Supabase 풀러(R8)는 아직 확인 못 함. ② 청크 크기는 측정 전 기본값. ③ 민감 패턴은 휴리스틱(오탐·미탐 가능). ④ 문서 하나가 바뀌면 그 문서 전체를 다시 임베딩(청크 단위 재사용은 하루 변경량을 실측한 뒤 판단). ⑤ cleaner 규칙을 바꾸면 모든 content_hash가 달라져 전체 재색인된다. ⑥ 단일 프로세스 가정(락으로 보장).

## 3. 아키텍처

```
Notion ──(배치 1회/일)──> 수집·청크 ──> embedder(KURE-v1) ──> Supabase pgvector
질문 ──> chat(Vercel) ──> 질문 임베딩(embedder, 터널) ──> pgvector 검색 ──> 근거+출처로 LLM 답변
                              └ embedder 불가/검색 실패 시 → 근거 없이 일반 답변(안전한 실패)
```

적용하는 원칙: 안전한 실패 구조 / 근거가 있을 때만 출처 표기, 없으면 "관련 문서에서 답을 찾지 못했다"고 알림 /
로그에 질문·문서 본문 미기록 / 문서 안 지시문 무시(프롬프트 인젝션 방어) / 스키마는 추가만, 코드 배포 전에 DB 먼저 /
환경변수 공백·따옴표 정리, CORS 허용 목록은 쉼표 뒤 공백 처리.

## 4. 위험과 열린 질문

- **R1. 문서 노출 범위(가장 중요)**: SM Pay 사용자에 대행사 등 외부 사용자가 포함되면 내부 설계·정책 문서가 답변으로 나갈 수 있다.
  → 전체 수집이 아니라 **수집 대상 루트 페이지 허용 목록(allowlist)** 으로 제한. *(2026-10-16 사용자 동의. 단 "챗 사용자에 대행사 등 외부 사용자가 포함되는가"는 아직 미확인 → 6단계(UI 연동) 전에 확인)*
- **R2. 터널 안정성·노출**: 임시 터널은 URL이 바뀌고 회사 PC가 인터넷에 노출된다. 고정 도메인 터널 + 비밀 헤더 + 호출 제한 필요.
  질문 임베딩도 요청마다 embedder를 거치므로 지연이 생긴다.
- **R3. embedder 단일 장애점**: 꺼지면 모든 질문이 "근거 없이 일반 답변"이 된다. 이때 사용자에게 근거 없음을 알려야 한다.
- **R4. 외부 전송 허용과의 관계**: 임베딩을 데스크탑에서 돌리는 이유는 보안이 아니라 모델 선택(KURE-v1 한국어 성능)·비용이다. 호스팅 임베딩 API도 대안으로 남겨둔다.
- **R5. 규모 미파악**: 문서 수·길이를 먼저 세어야 청크 크기와 배치 시간을 정할 수 있다 → A5의 첫 작업.
- **R6. Intel Mac 제약**: torch 2.2.2 상한 → 호환 조합을 검증해 고정했다 (A1 완료, 위 결정 표). 단 KURE-v1 실제 로딩은 아직 미검증 → A2에서 확인. 구버전 조합이라 최신 기능·보안 패치는 못 받는 점은 감수.
- **R7. Vercel 서버리스 한계**: 번들 크기·실행 시간 제한, 스트리밍 지원 범위를 A8 전에 확인한다.
- **R13. 최초 백필 시간**: 청크당 약 1.5초(맥북 기준, 컨테이너도 비슷)라 1,500청크면 약 40분, 10,000청크면 약 4.3시간. 데스크탑이 절전에 들어가면 중단된다(Windows 전원 설정은 B2). `--dry-run`으로 예상 청크 수를 먼저 확인하고, `--limit`으로 나눠 돌릴 수 있으며 재실행하면 이어서 처리된다.
- **R14. 모델 교체 절차**: 검색은 같은 revision의 청크만 비교하므로 임베딩 서버를 새 revision으로 바꾸면 **재색인이 끝나기 전까지 일부 문서만 검색된다**. 절차: 새 서버 배포 → `sync --force-reindex`. 그 사이의 빈 검색 결과는 A8의 "근거 없이 답변" 경로가 받는다.
